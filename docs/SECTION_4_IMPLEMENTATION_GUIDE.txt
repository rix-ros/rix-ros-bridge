OVERVIEW
================================================================================

WHAT: Bridge handles manage one-directional message flow
GOAL: Subscribe to one side, convert messages, publish to other side

DELIVERABLES:
  ✓ BridgeHandleRosToRix - ROS subscriber → RIX publisher
  ✓ BridgeHandleRixToRos - RIX subscriber → ROS publisher

ANALOGY: Postal workers at border who receive mail, translate it, forward it

WHY TWO HANDLES? 
  - Bidirectional = Two one-way bridges
  - Easier to test independently
  - Clean separation of concerns

USES SECTION 3: Both handles call StringConverter methods

IMPORTANT - ECHO-BACK PREVENTION:
  Each handle uses SEPARATE topic names for subscribe and publish to prevent
  infinite loops where the bridge echoes its own messages back and forth.
  
  Example configuration:
    ROS→RIX: Subscribe to /chatter (ROS) → Publish to /chatter_from_ros (RIX)
    RIX→ROS: Subscribe to /chatter (RIX) → Publish to /chatter_from_rix (ROS)
  
  This prevents the RIX→ROS handle from seeing messages published by ROS→RIX
  handle and vice versa.

================================================================================
HOW IT ALL WORKS TOGETHER
================================================================================

BIDIRECTIONAL ARCHITECTURE (WITH ECHO-BACK PREVENTION):

    ROS System              Bridge Handles              RIX System
        │                                                   │
    /chatter ────────► BridgeHandleRosToRix ────────► /chatter_from_ros
        │                (subscribe ROS,                    │
        │                 publish RIX)                      │
        │                                                   │
/chatter_from_rix ◄─── BridgeHandleRixToRos ◄────────  /chatter
                       (subscribe RIX,
                        publish ROS)

NOTE: Different publish topic names prevent infinite echo-back loop!

EXAMPLE: ROS publishes "Hello"
  1. ROS publisher sends String(data="Hello") to /chatter
  2. BridgeHandleRosToRix.ros_callback() triggered (subscribed to /chatter)
  3. Calls StringConverter.ros_to_rix() → RixString(data="Hello")
  4. Publishes to RIX /chatter_from_ros (NOT /chatter!)
  5. RIX subscribers on /chatter_from_ros receive "Hello"
  6. RIX→ROS handle ignores this (subscribes to /chatter, not /chatter_from_ros)
  ✓ NO ECHO-BACK LOOP!

EXAMPLE: RIX publishes "World"
  1. RIX publisher sends RixString(data="World") to /chatter
  2. BridgeHandleRixToRos.rix_callback() triggered (subscribed to /chatter)
  3. Calls StringConverter.rix_to_ros() → String(data="World")
  4. Publishes to ROS /chatter_from_rix (NOT /chatter!)
  5. ROS subscribers on /chatter_from_rix receive "World"
  6. ROS→RIX handle ignores this (subscribes to /chatter, not /chatter_from_rix)
  ✓ NO ECHO-BACK LOOP!

ERROR HANDLING:
  - Try/except in callbacks catches errors
  - One bad message doesn't crash bridge

================================================================================
ECHO-BACK PREVENTION STRATEGY
================================================================================

WHY IT MATTERS:
  Without separate topic names, the bridge would create an infinite loop:
  
  External ROS publisher → /chatter (ROS)
    → Bridge ROS→RIX → /chatter (RIX)
    → Bridge RIX→ROS → /chatter (ROS)  ← Bridge sees its own message!
    → Bridge ROS→RIX → /chatter (RIX)  ← Loop continues forever!
  
  This would:
    - Flood the network with duplicate messages
    - Consume all CPU resources
    - Make the bridge unusable
    - Crash the system

SOLUTION IMPLEMENTED:
  Use different topic names for subscribe vs publish:
  
  ROS→RIX Handle:
    Subscribe to:  /chatter (ROS)           ← External messages only
    Publish to:    /chatter_from_ros (RIX)  ← Different name!
  
  RIX→ROS Handle:
    Subscribe to:  /chatter (RIX)           ← External messages only
    Publish to:    /chatter_from_rix (ROS)  ← Different name!
  
  Result: Each handle only sees EXTERNAL messages, never its counterpart's output!

TESTING COMMANDS FOR DEMO:
  # Test ROS → RIX bridging
  ros2 topic pub /chatter std_msgs/msg/String "data: 'Hello from ROS'"
  # Listen on RIX: /chatter_from_ros
  
  # Test RIX → ROS bridging
  # Publish on RIX: /chatter
  ros2 topic echo /chatter_from_rix
