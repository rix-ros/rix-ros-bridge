Lines 143-148: **DUAL SPIN LOOP** (CRITICAL!)
  while rclpy.ok():
      # Process ROS events
      rclpy.spin_once(bridge, timeout_sec=0.1)
      
      # Process RIX events
      bridge.spin_once()

WHY DUAL SPINNING:
  - ROS and RIX are separate middleware systems
  - Each has its own event loop
  - Must process both to handle callbacks from both sides

HOW IT WORKS:
  1. rclpy.spin_once(bridge, timeout_sec=0.1)
     - Processes ROS callbacks (ros_callback in ROS→RIX handle)
     - timeout_sec=0.1: Wait up to 100ms for ROS events
     - Returns after timeout even if no events
  
  2. bridge.spin_once()
     - Processes RIX callbacks (rix_callback in RIX→ROS handle)
     - Non-blocking (timeout=0.0 in implementation)
     - Returns immediately
  
  3. Loop repeats while rclpy.ok() is True

LOOP FREQUENCY: ~10 Hz minimum (due to 0.1s ROS timeout)
  - Fast enough for responsive bridging
  - Not so fast as to waste CPU

================================================================================
HOW IT ALL WORKS TOGETHER
================================================================================

STARTUP SEQUENCE:

1. User runs: ros2 run rix_ros_bridge bridge_node
2. ROS2 calls: rix_ros_bridge.bridge_node:main
3. main() executes:
   a. rclpy.init()
   b. bridge = RixRosBridge()
      - super().__init__('rix_ros_bridge') → ROS node created
      - self.rix_node = rix.core.Node() → RIX node created
      - _create_bridge_handles() called:
        * BridgeHandleRosToRix created
        * BridgeHandleRixToRos created
        * Both handles started
          - ROS→RIX: subscribes to ROS /chatter, publishes to RIX /chatter_from_ros
          - RIX→ROS: subscribes to RIX /chatter, publishes to ROS /chatter_from_rix
   c. Spin loop starts

RUNTIME (Dual Spin Loop):

  while rclpy.ok():
      rclpy.spin_once()    → Process ROS events
          ↓
      If ROS message on /chatter:
          → ROS→RIX handle's ros_callback() triggered
          → Converts & publishes to RIX /chatter_from_ros
      
      bridge.spin_once()   → Process RIX events
          ↓
      If RIX message on /chatter:
          → RIX→ROS handle's rix_callback() triggered
          → Converts & publishes to ROS /chatter_from_rix
      
      Loop repeats...

SHUTDOWN SEQUENCE:

1. User presses Ctrl+C
2. KeyboardInterrupt raised
3. except KeyboardInterrupt: block catches it
4. finally: block executes:
   a. bridge.shutdown() called:
      - ros_to_rix_handle.stop() → Destroys ROS subscriber
      - rix_to_ros_handle.stop() → Destroys ROS publisher  
      - self.rix_node.shutdown() → Shuts down RIX node
   b. rclpy.shutdown() → Shuts down ROS
5. Program exits cleanly

================================================================================
KEY DESIGN DECISIONS
================================================================================

WHY INHERIT FROM RosNode?
  - Bridge needs to be a ROS node to create ROS pub/sub
  - Provides get_logger() for logging
  - Integrates with rclpy.spin_once()

WHY SEPARATE RIX NODE?
  - RIX and ROS are independent systems
  - Can't inherit from both (Python doesn't support multiple inheritance this way)
  - RIX node as member variable works perfectly

WHY DUAL SPIN LOOP?
  - ROS and RIX have separate event loops
  - Must process both to handle callbacks from both sides
  - Alternative (threads) more complex and unnecessary

WHY timeout_sec=0.1 FOR ROS?
  - Balance between responsiveness and CPU usage
  - 100ms is fast enough for most applications
  - Allows ~10 Hz loop frequency minimum

WHY timeout=0.0 FOR RIX?
  - Non-blocking to avoid delays
  - ROS timeout already controls loop frequency
  - Process available RIX events immediately

WHY SEPARATE TOPICS?
  - Prevents infinite echo-back loop
  - /chatter vs /chatter_from_ros/rix
  - Each handle only sees external messages
